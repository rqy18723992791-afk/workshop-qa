# 检索与拒答阈值设计说明

> 对应代码：`backend/app/services/kb.py`、`backend/scripts/calibrate.py`
> 答辩可讲清的一句话：**把问题和知识库切片都变成 bge-m3 向量，用余弦相似度找最接近的几段；最高分低于 0.6 就认为知识库答不了，这个 0.6 是拿 30 条问句实测出来的，不是拍脑袋定的。**

## 1. 为什么用向量检索，而不是关键词搜索

车间提问和手册写法经常对不上：

- 工人说「料筒温度上不去」，手册写「加热圈开路 / 加热不足」；
- 工人说「产品边缘有毛刺」，手册写「飞边」；
- 同一个意思可能用「模温」「模具温度」「料温」等不同说法。

关键词搜索要求字面重合，换一种说法就搜不到。向量检索比较的是**语义相近程度**：bge-m3 把中文句子映射成 1024 维向量，意思接近的句子在向量空间里距离近，不依赖字面相同。

## 2. 检索流程

```
用户问题
  → embed_query()：调用 Ollama 的 bge-m3，得到 1024 维向量
  → Chroma collection.query(n_results=4)
  → 每条结果的距离 distance 转成相似度 score = 1 - distance
  → max_score = 所有命中片段的最高分
  → max_score >= 0.6 ? has_relevant=true : false
  → 返回 hits（原文、文档名、编号、章节、分数）给问答层
```

### 2.1 为什么是 `1 - distance`

Chroma 的 cosine 空间返回的是**余弦距离**，范围 0～2：

- 完全同向：distance = 0 → score = 1；
- 完全无关：distance = 1 → score = 0；
- 完全相反：distance = 2 → score = -1（中文问答里几乎不会出现）。

前端和校准记录里看到的 0.78、0.66 都是 `1 - distance` 后的相似度，数值越大越相关。这样展示符合直觉，也方便和阈值直接比较。

### 2.2 为什么 top_k = 4

- 一个具体操作问题通常只需要 1～2 个章节就能回答；
- 4 段约 500～1000 字，既能覆盖同一问题的不同侧面，又不会把 7B 模型的 4K 上下文挤满；
- 实测调大到 6 段时，回答质量没有明显提升，首字延迟却增加；
- 调小到 2 段时，「开机前检查」这类跨文档问题会漏掉安全规程。

`top_k` 可通过 `RETRIEVAL_TOP_K` 调整，接口也允许单次请求覆盖。

## 3. 阈值 0.6 是怎么定出来的

### 3.1 先承认一个事实：没有唯一正确的阈值

相似度阈值不是模型自带的参数，而是**业务判断**：误收一条无关资料，可能让模型编造答案；误拒一条有用资料，用户会觉得系统「什么都不知道」。阈值本质上是在这两种错误之间选平衡点。

### 3.2 30 条问句的校准实验

`backend/scripts/calibrate.py` 构造了三组问题：

| 组别 | 数量 | 目的 | 例子 |
| --- | --- | --- | --- |
| 正向 | 15 | 知识库明确能回答 | 注塑机开机前需要检查什么 |
| 负向 | 8 | 与注塑车间无关 | 如何做红烧肉、手机屏幕碎了怎么办 |
| 灰区 | 7 | 注塑相关但知识库没写 | 注塑机多少钱一台、螺杆多久更换 |

每组只做检索、不调用生成模型，记录 top-1 相似度。结果（2026-11-05，完整数据见 [calibration-data.json](calibration-data.json)）：

| 指标 | 数值 |
| --- | --- |
| 正向最低分 | **0.675** |
| 正向平均分 | 0.754 |
| 负向最高分 | **0.522** |
| 负向平均分 | 0.378 |
| 灰区范围 | 0.436～0.617 |

正向最低 0.675 高于负向最高 0.522，中间存在一段**安全带** `[0.522, 0.675]`。只要阈值落在这段区间内，就能把 15 条正向全部放行、8 条负向全部挡住。

### 3.3 为什么取中点 0.6，而不是 0.675 或 0.522

- 取 0.675：正好压在正向样本的最低分上，换一批问法就可能误拒；
- 取 0.522：正好压在负向样本的最高分上，换一批无关问题就可能误收；
- 取中点 0.6：两侧各留约 0.075 的余量，对样本波动更稳。

第一次校准脚本直接推荐了 0.675（最小正向分），属于对样本过拟合；后来改成「存在安全带时取中点」，才得到 0.6。这个过程也写进了 [calibration.md](calibration.md)，答辩时可以讲「我们不是调出一个好看的数字，而是发现并修正了过拟合」。

### 3.4 旧阈值 0.5 的问题

最初凭经验用了 0.5。校准时发现「手机屏幕碎了怎么办」的相似度是 **0.522**，会被放行；虽然生成层大概率会拒答，但检索层已经把无关资料送进了模型上下文，增加了编造风险。0.6 能直接把它挡在检索层。

## 4. 阈值不是万能的：两层拒答

灰区问题（注塑相关、知识库没写）的分数可能落在 0.6 附近。例如「注塑机多少钱一台」可能过阈值，但资料里没有价格。因此系统用两层：

1. **检索层**：`max_score < 0.6` → 直接拒答，不调用大模型；
2. **生成层**：过了阈值，但本地模型判断资料不足 → 输出固定拒答语。

端云协同模式下，这两类低置信情况还会触发云端升级，见 [routing.md](routing.md)。

## 5. 关键取舍

| 选择 | 取舍 |
| --- | --- |
| 单一全局阈值 | 简单、可解释；但不同类别文档的分数分布可能不同，未来可按类别分别校准 |
| bge-m3 | 中文语义强、支持长文本；模型约 1.2 GB，首次加载慢，之后常驻 |
| 不做 rerank | 少一个模型、少一层延迟；当前 15 份文档规模下 top-4 已够用，文档上千后应加 cross-encoder 重排 |
| 分数只用于判断 | 不把分数直接展示成「置信度百分比」，避免用户误解为概率 |

## 6. 怎么复现与调试

```bash
# 重新跑 30 条校准（需要后端与 Ollama 已启动）
backend/.venv/Scripts/python.exe backend/scripts/calibrate.py

# 单条检索，直接看分数和片段
curl -X POST http://127.0.0.1:8000/api/kb/search \
  -H "Content-Type: application/json" \
  -d '{"query":"料筒温度异常怎么排查","top_k":4}'
```

前端「知识库 → 检索测试台」也直接展示 top-4、相似度和阈值，演示时可以现场改问题观察分数变化。

## 7. 答辩可能被问到的问题

- **0.6 是模型给的默认值吗？** 不是。Chroma 和 bge-m3 都没有「拒答阈值」这个概念，0.6 是我们用 30 条标注问句校准出来的业务参数。
- **换一批文档，阈值还成立吗？** 不一定。文档风格、切分粒度变化都会改变分数分布，需要重新跑校准脚本；这也是我们把校准过程做成脚本而不是写死一个数的原因。
- **为什么负向问题也能得到 0.5 左右的分？** 中文向量模型会把「注塑机」和「红烧肉」都映射到「烹饪/设备」等泛语义空间，完全无关也可能有基础分；所以阈值必须靠实测，不能设 0。
- **检索错了怎么办？** 检索层挡低分，生成层挡「高分但无答案」，云端再兜底领域相关但资料不足的问题；三层配合，而不是指望一个阈值解决所有情况。
