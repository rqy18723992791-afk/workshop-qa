# 故障排查状态机设计说明

> 对应代码：`backend/app/services/diagnosis.py`、`backend/app/routers/diag.py`、`frontend/src/components/DiagnosisView.vue`
> 答辩可讲清的一句话：**把设备手册里的排查步骤写成一张有向图，每个节点是一个检查项，选项指向下一个节点或结论；后端只负责按图走、记录过程、生成处置单，不依赖大模型自由发挥。**

## 1. 为什么不用「让大模型自己一步步问」

大模型做多轮追问很自然，但这个场景有三个硬约束：

1. **安全**：电气、高温检查顺序错了可能伤人。第一步必须是安全确认，不能由模型「觉得」可以跳过。
2. **可审计**：处置单要能给设备科看，每一步为什么问、依据哪本手册哪一节，必须固定可查。
3. **可复现**：同一个症状、同样的回答，应该得到同样的结论；大模型每次措辞不同，不适合作为流程控制器。

所以这里把「流程控制」交给确定性的状态机，把「自然语言解释」留给问答模块。两者分工明确：状态机保证正确路径，问答保证知识覆盖。

## 2. 数据结构：节点、选项、结论

整条链写在 `_TOPICS` 这个字典里，不改代码就能加主题：

```python
node = {
    "title": "加热圈电阻",
    "question": "测量该区加热圈冷态电阻，读数是多少？",
    "hint": "测量前拔下接线，手不要接触表笔金属部分。",
    "basis": [B_HEATER],          # 手册原文依据
    "options": [
        _opt("normal", "35～45 Ω（正常范围）", "terminal_inspect", "safe"),
        _opt("open", "无穷大或明显大于 100 Ω", "conclusion:heater_open", "danger"),
        _opt("unknown", "还没测 / 不会测", "measure_guide"),
    ],
}
```

三个关键设计：

- **选项用 `next` 指向下一个节点**：普通字符串是节点 ID；带 `conclusion:` 前缀表示直接到结论。这样图的拓扑完全由数据描述，前端不需要知道任何业务分支。
- **每个节点带 `basis`**：引用 `FC-T-001` 的原文，前端在问题下方展示「手册依据」，答辩时能说清「为什么问这个」。
- **选项带 `tone`**：`safe / warn / danger` 只影响界面颜色，不参与逻辑，避免把展示和业务耦合。

当前主题 `temp-anomaly`（料筒温度异常 A-101）包含 **12 个节点、11 个结论**，覆盖单区降温、温度波动、局部过热、多区同时下降四类现象。

## 4. 一次会话的生命周期

```
POST /api/diag/sessions          → 创建 session，返回第一步节点
POST /api/diag/sessions/{id}/answer
   body: { node_id, option_id }
   → 校验 node_id 是否是当前节点（防止前端重复提交/错位）
   → 记录一步 history
   → next 是普通节点：返回下一题
   → next 是 conclusion：生成 report，返回 done=true
POST /api/diag/sessions/{id}/back → 弹出 history 栈顶，回到上一步
GET  /api/diag/sessions/{id}/report.md → 下载 Markdown 处置单
```

### 4.1 会话存储

- 存在进程内存的 `_sessions` 字典里，加 `threading.Lock`；
- 每条会话 2 小时 TTL，每次访问时清理过期会话；
- 会话结构：`topic_id / current_node / history[] / conclusion / created_at / completed_at`；
- **取舍**：不引入 Redis，单机演示足够；代价是服务重启会话丢失、无法多副本。生产扩容时把 `_sessions` 换成 Redis 即可，接口不变。

### 4.2 回退

`history` 是栈：每答一步压入「节点 ID、问题、答案」。回退时弹出最后一条，把 `current_node` 指回该节点，同时清空结论和报告。这样用户改一个答案，后面的分支会重新走，不会残留旧结论。

### 4.3 报告编号

格式 `CZ-YYYYMMDD-XXXXXX`，后 6 位是随机十六进制。演示时能看出日期，方便和设备科纸质单对应；随机后缀避免同一天多份报告重号。

## 5. 处置单里有什么

`_report()` 把会话整理成结构化 JSON：

| 字段 | 内容 |
| --- | --- |
| `report_no` | 处置单编号 |
| `topic` | 设备、故障主题 |
| `symptom` | 第二步选择的故障现象 |
| `process[]` | 每一步的检查项、用户回答、手册依据 |
| `conclusion` | 结论标题、等级、说明、处置建议、安全提示 |
| `references[]` | 所有引用去重后的文档名、编号、章节、原文 |

前端把 JSON 渲染成可打印的 A4 处置单；`report_markdown()` 用同一份数据生成 Markdown，保证网页、打印、导出三种形态内容一致。打印样式在 `@media print` 下切成白底黑字，并通过 `@page { size: A4; margin: 0 }` + 14mm 内边距控制版心，避免浏览器默认页边距把右侧编号裁掉。

## 7. 取舍与后续

| 选择 | 取舍 |
| --- | --- |
| 固定选项，不做自由文本 | 保证分支可控、可审计；代价是表达受限，后续可用 LLM 把自由描述映射到选项 |
| 单主题先做深 | 先把一条链的手册依据、结论、处置单打磨完整；顶出/液压/模具保护可复用同一引擎 |
| 内存会话 | 简单、零依赖；重启丢失，生产多副本需 Redis |
| 规则式结论 | 可解释、可追责；不排除未来用模型做「结论措辞润色」，但分支判断仍由状态机负责 |

## 8. 答辩可能被问到的问题

- **这算 Agent 吗？** 算「工作流型 Agent」：有状态、有分支、有工具（知识库/手册）、有结构化产出。它不靠模型自由规划，而是把领域专家的排查路径固化成图，更适合安全敏感场景。
- **为什么只有一条诊断链？** 先把一条链做到「每步有依据、结论可导出、能回退」，验证引擎；其余主题是往 `_TOPICS` 加数据，不是重写代码。比赛时间优先保证深度而不是数量。
- **用户瞎选怎么办？** 选项都对应现场可观察的事实（电阻读数、端子状态、是否导通），并配「不会测/无法判断」出口，直接转设备科；不逼迫用户猜。
- **结论错了谁负责？** 处置单明确写「处置前请由设备主管复核」，安全提示要求持证人员操作；系统定位是辅助排查，不是替代设备科。
