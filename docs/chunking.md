# 文档切分与入库设计说明

> 对应代码：`backend/app/services/chunking.py`、`backend/app/services/kb.py`
> 答辩可讲清的一句话：**按标题切节、按段落切块、块间留重叠，每个块都带着"它来自哪份文档的哪一章"的上下文进入向量库。**

## 1. 要解决什么问题

车间文档不是流水账，而是有结构的操作规程、点检表、故障案例卡。检索时用户问"温度异常怎么排查"，理想命中不是"包含温度两个字的所有段落"，而是**故障案例卡中"排查步骤"这一节**。因此切分目标有两个：

1. **语义完整**：一个块尽量是一段完整的操作步骤或一条完整的原因说明，不要在一句话中间切断；
2. **自带上下文**：每个块要能回答"我是谁、我来自哪"——否则"检查加热圈电阻"这样的块脱离标题后，向量模型无法知道它属于温度故障还是日常点检。

## 2. 具体做法

### 第一步：解析文首元数据

每份文档以 `---` 包裹的元数据块开头（文档名、文档编号、类别、版本、日期）。代码逐行解析，把中文键名映射成内部英文字段，正文从第二个 `---` 之后开始。没有元数据块的文档也能导入，用文件名兜底。

**为什么用文档编号做 doc_id**：编号是车间文档的唯一业务标识，换文件名不影响索引；重复导入同一编号时先删旧块再写入，天然幂等。

### 第二步：按 Markdown 标题切节

扫描 `##`～`####`，维护一个标题栈。遇到同级或更高级标题就出栈，最终得到形如 `三、可能原因 > 3.2 加热圈检查` 的章节路径。H1（文档大标题）不进路径，因为文档名已由元数据提供。

**为什么先切标题**：标题是作者亲手划定的语义边界，比任何算法猜测都可靠。一份故障案例卡的"故障现象 / 可能原因 / 排查步骤 / 处置措施"四节，恰好对应诊断时需要的四类信息。

### 第三步：节内按空行切段，段落超长才硬切

文本按空行拆成段落，逐段累加；超过 `CHUNK_SIZE`（默认 600 字符）就先输出当前块，下一块用上一块末尾 `CHUNK_OVERLAP`（默认 80 字符）开头，再拼接新段落。

- **段落优先**：中文技术文档的段落通常就是一条完整意思（一个步骤、一条原因），按段落切几乎不会切断语义；
- **重叠 80 字**：防止答案恰好跨在块边界上。80 字约等于一两句话，足够衔接，又不会让相邻块高度重复；
- **超长段落**（如大表格）才退化为定长窗口切分，窗口内部同样保留重叠。

### 第四步：为向量化文本拼接上下文

每个块存两份文本：

- `text`：原始正文，用于界面展示引用片段；
- `embed_text`：`文档名｜类别｜章节路径\n正文`，只用于向量化。

**为什么分开**：检索相似度需要文档级语义（比如"注塑机锁模安全规程"这一语境），但引用展示必须忠于原文，不能把拼接前缀混进给用户看的片段里。

## 3. 关键参数与依据

| 参数 | 默认值 | 依据 |
| --- | --- | --- |
| `CHUNK_SIZE` | 600 字符 | 中文 600 字约 400～500 token，bge-m3 上限 8192 token，远未触顶；同时保证一个块通常是一节内容，不会太碎 |
| `CHUNK_OVERLAP` | 80 字符 | 约一两句话，足够跨块衔接，重复率可控 |
| `EMBED_BATCH` | 16 | 单次请求 16 条，兼顾吞吐与显存/内存占用；失败时只需重试一小批 |
| 向量库距离 | 余弦 | 文本向量关注方向而非长度，余弦是语义检索的常规选择 |
| `RETRIEVAL_TOP_K` | 4 | 4 个块约覆盖 500～1000 字上下文，够回答一个具体操作问题，又不会让上下文塞满小模型的 4K 窗口 |
| `RETRIEVAL_MIN_SIM` | 0.5 | 11-06 实测校准：12 个正向问题最低 0.534；10 个无关问题平均 0.414，但"注塑机多少钱一台"达 0.607。单一阈值无法完全分开，取 0.5 保召回，精确拒答在生成阶段兜底 |

## 4. 取舍与备选方案

- **不用固定长度窗口**：实现简单但会把步骤、表格拦腰切断，且丢失标题语义；实测本知识库 15 份文档按标题+段落切分共 **123 个块，平均约 140 字，最长 600 字**，粒度适合"一问一答一出处"。
- **不做父子块/多级检索**：父子块（小块检索、大块喂给模型）能兼顾精度与上下文，但需要两套存储与额外逻辑。当前知识库规模小、文档结构清晰，先用单级块 + `embed_text` 前缀达到类似效果；若 11-07 实测召回不足，再升级为"小节块检索、整节回填"。
- **块偏小是刻意的**：检索精度优先，宁可多召回几块，也不让一个块混入多个主题。生成阶段会把 top-k 块按文档聚合后拼上下文（11-07 实现）。
- **不做语义切分模型**：引入额外模型会增加显存与离线部署负担，Markdown 标题已经提供了高质量结构信号。

## 5. 如何验证

1. 运行切分自测：15 份文档全部解析出正确的文档编号/类别/版本/日期，切片数 123；
2. 检查边界：任取一个跨段落的块，确认块间有 80 字重叠且首尾句子完整；
3. 入库后用"注塑机开机前需要检查什么""模具保护报警怎么处理""今天股票行情"三类问题检索，观察相关文档得分是否显著高于无关问题（服务端日志会打印 `max_score`）。

## 6. 答辩可能被问到的问题

- **为什么不用 LangChain 的 RecursiveCharacterTextSplitter？** 它的分隔符优先级是段落/句子/字符，不理解 Markdown 标题层级，也不保留章节路径；我们的文档结构价值恰在标题，自己实现不到 150 行，逻辑完全可控。
- **600 字怎么定的？** bge-m3 支持长文本，但块越大主题越杂、检索越糊；600 字对应本知识库约 1～2 个自然段，实测平均块长 140 字，600 只是上限而非目标。
- **重叠会不会导致重复引用？** 会在相邻块出现少量重复文字，但引用展示时按 `doc_id + chunk_index` 去重，且用户看到的是原文片段，不影响可读性。
